## 2. 项目阶段划分

项目采用 **门径式（Stage-Gate）+ 迭代式** 混合管理：阶段间设置冻结门径（Gate），阶段内采用短迭代交付。

| 阶段 | 名称 | 时间窗口 | 核心目标 | 出口门径（Gate） | 状态 |
|---|---|---|---|---|---|
| Phase 0 | 立项 | T0 ~ T0+2周 | 明确项目定位、可行性、资源与干系人 | G0 立项批准 | 已完成 |
| Phase 1 | 需求 | T0+2周 ~ T0+4周 | 完成需求调研、MoSCoW 分级、需求冻结 | G1 需求冻结（M1） | 已完成 |
| **Phase 2** | **设计** | **T0+4周 ~ T0+8周** | 架构、数据库、接口、管线、Agent、评估设计 | **G2 设计冻结（M2）** | **进行中（当前）** |
| Phase 3 | 开发 | T0+8周 ~ T0+20周 | MVP → V1 功能实现（MVP 4周 / V1 8周） | G3 MVP 功能完成（M3） | 未开始 |
| Phase 4 | 测试 | T0+18周 ~ T0+22周 | 集成测试、评估门禁、安全测试、UAT | G4 质量达标 | 未开始 |
| Phase 5 | 部署上线 | T0+22周 ~ T0+24周 | 私有化部署、压测、灰度、正式上线 | G5 生产上线（M4） | 未开始 |
| Phase 6 | 运营迭代 | T0+24周 ~ T0+34周 | V2 迭代（12周）、运营优化、收尾移交 | G6 项目收尾（M8） | 未开始 |

> **当前状态结论**：项目处于 **Phase 2 设计阶段**，进度约 `T0+6周`，距离设计冻结（M2，T0+8周）剩余 **2 周**。

### 2.1 阶段门径评审规则

1. 每个 Gate 必须由 **项目经理 + 架构师 + 产品经理** 三方签署方可通过。
2. 未通过 Gate 的阶段产出不进入下一阶段，缺陷项记入风险登记册并跟踪。
3. 设计阶段冻结后，任何影响架构/接口的变更须走 **变更控制流程**（见基线第 2 节）。

## 5. 迭代计划

项目采用 **MVP → V1 → V2** 三段迭代，对应基线阶段归属。

### 5.1 MVP 迭代（4 周，T0+8周 ~ T0+12周）

**目标**：跑通「上传 → 解析 → 检索 → 问答 → 引用」最小闭环，验证核心价值。

**范围**：

- `kb` 基础空间/文档/权限；`ingestion` 最小管线（PDF/Word 解析）；`retrieval` 混合检索+Rerank；
- `agent` 单智能体意图路由与工具调用；`tools` 内置工具 + MCP 基础接入；
- `memory` 短期会话；`citation` 片段引用与跳转；`admin` Langfuse 追踪；
- 前端：知识库管理、对话问答、管理后台最小可用。

**验收标准**：≥3 业务域、≥1000 份文档可检索；引用准确率 ≥90%；无依据回答率 ≤5%。

### 5.2 V1 迭代（8 周，T0+12周 ~ T0+20周）

**目标**：从「能用」到「企业级可用」，补齐权限、审计、规模化与生产运维。

**范围**：

- `ingestion` 增量更新与知识同步；`retrieval` 检索质量调优与 A/B；
- `agent` 多智能体协同（Planner/Worker/Validator）；`tools` 扩展至 ≥50 个 API；
- `memory` 长期记忆；`admin` 审计日志与计费；前端开发者控制台；
- Kubernetes 生产部署、性能压测、安全测评。

### 5.3 V2 迭代（12 周，T0+20周 ~ T0+32周）

**目标**：智能化增强与平台化扩展，支撑规模化运营。

**范围**：

- `agent` 人工审批与回环；`tools` MCP 生态适配与安全网关；
- `admin` 在线评估与持续监控；多租户增强；
- 运营数据分析、模型成本优化、第三方集成生态。

## 6. 关键路径与依赖分析

### 6.1 关键路径

**关键路径**（总工期最长、无浮动时间的串行链）：

```
需求冻结(M1) → 架构设计(2) → 检索引擎(6) → Agent编排(7) → 工具与MCP(8)
→ 测试与评估门禁(13) → 部署上线(M4)
```

**关键路径说明**：检索质量直接决定 `agent` 编排效果与 `citation` 可信度，是本项目最大技术不确定项，故列为关键路径核心。

### 6.2 主要依赖关系

| 依赖编号 | 前置工作包 | 后续工作包 | 依赖类型 | 说明 |
|---|---|---|---|---|
| D1 | 1 需求 | 2 架构 | FS（完成-开始） | 需求冻结后方可定架构 |
| D2 | 2 架构 | 3 数据库、4 接口、5 管线 | FS | 模块边界确定后展开 |
| D3 | 6 检索 | 7 Agent、10 引用 | FS | 检索结果决定 Agent 上下文 |
| D4 | 7 Agent | 8 工具 | FS | 工具调用由 Agent 编排触发 |
| D5 | 4 接口 | 12 前端 | FS | 前端依赖接口契约 |
| D6 | 3~12 | 13 测试 | FS | 测试覆盖全模块 |
| D7 | 14 部署 | M4 上线 | FS | 部署完成方可上线 |
| D8 | 11 评估 | M4 上线 | FS | 评估门禁是上线前置条件 |

### 6.3 依赖管理规则

1. 关键路径上的延迟 1 天 = 总工期延迟 1 天，须当日上报 PM。
2. 并行工作包（如 9 会话记忆 与 6 检索）之间通过 **接口契约** 解耦，契约冻结后并行开发。
3. 外部依赖（pgvector 向量库、LLM 供应商、MCP 生态）须在里程碑评审中单独跟踪。

| 发布评审 | 里程碑 | PM+AR+QA+OP | 评估门禁通过、回滚方案就绪 |

### 8.2 代码与工程规范

1. 统一 Java 21 + Spring Boot 3.2+（Spring WebFlux）工程骨架；接口、表名、字段名使用 **英文小写下划线**（基线第 6 节）。
2. 静态检查：Checkstyle + SpotBugs + SonarQube；格式：Spotless；提交规范：Conventional Commits。
3. 每次 LLM 调用必须有 trace（Langfuse），每次 RAG 结果必须有评估分数（基线 2.1）。
4. 密钥与配置不得硬编码，统一经 `admin` 配置中心管理。

### 8.3 测试覆盖与评估门禁

| 测试层级 | 覆盖率要求 | 说明 |
|---|---|---|
| 单元测试 | 后端核心 ≥75%，管线模块 ≥80% | 覆盖解析、切分、权限过滤 |
| 集成测试 | 关键链路 100% | 上传→检索→问答→引用全链路 |
| 检索质量评估 | 引用准确率 ≥90%，无依据回答率 ≤5% | 离线评估集 + 门禁 |
| 安全测试 | 越权、数据泄露用例 100% 通过 | 覆盖 4 种角色权限矩阵 |
| 性能测试 | 支持并发 ≥200、P95 首 token ≤3s | V1 阶段执行 |

### 8.4 评估门禁

- **上线门禁**：评估不达标不得上线，由 QA 一票否决。
- **回归门禁**：每个迭代结束跑全量评估集，指标劣化 >3% 则回滚。
- **质量红线**：引用准确率 <85% 或无依据回答率 >8% 时触发 **技术风险升级**。
