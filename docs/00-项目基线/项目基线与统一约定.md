# 项目基线与统一约定

> 本文档是「星枢 Nexus · 企业智能知识库与问答智能体平台」的**唯一权威基线**。
> 所有需求、设计、计划、交接文档在描述技术栈、模块命名、术语时，必须与本文档保持一致。
> 版本：v0.2（设计阶段） ｜ 最后更新：2026-10-29 ｜ 状态：基线冻结
> 变更说明：v0.2 将技术栈从 Python 切换为 **Java 生态**（用户背景为 Java）；v0.1 的 Python 方案已作废。

## 1. 项目概述

| 项 | 内容 |
|---|---|
| 项目名称 | 星枢 Nexus · 企业智能知识库与问答智能体平台 |
| 英文代号 | NKAP（Nexus Knowledge Agent Platform） |
| 项目定位 | 面向 B 端企业客户的私有化 / 混合部署 AI 知识平台 |
| 一句话描述 | 把企业内部分散的文档统一接入，通过 **RAG + Agent 编排**，为员工提供**可溯源、带权限、可扩展**的智能问答与业务协同能力 |
| 目标阶段 | 当前处于 **设计阶段（Phase 2）**，尚未进入编码 |
| 交付形态 | 企业级私有化部署 + OpenAPI 开放平台 |

### 1.1 解决的业务问题

1. **知识分散**：制度、SOP、产品文档、技术资料散落在 Wiki / 网盘 / 群聊中，检索靠人工。
2. **回答不可信**：传统关键词检索只给链接，员工仍需自行阅读、判断，无法直接得到带出处的答案。
3. **重复劳动**：HR、IT、客服、运维等支持类岗位大量重复解答相同问题。
4. **权限与合规**：知识库一旦接入 AI，必须保证「谁能问、能问什么、能看到哪段原文」可控可审计。
5. **接入成本高**：业务系统工具不统一，AI 难以调用真实业务数据。

### 1.2 项目目标（北极星指标）

- **核心目标**：员工在 2 个点击内获得「带原文引用、可验证」的问题答案。
- **效率目标**：支持类岗位重复咨询量下降 **30%**。
- **覆盖目标**：首期接入 ≥ 3 个业务域、≥ 1000 份文档、≥ 50 个 API 工具。
- **质量目标**：RAG 回答引用准确率 ≥ 90%，无依据回答率 ≤ 5%。

## 2. 统一技术栈（冻结，Java 生态）

> 未经评审不得变更；确需变更须在本文档追加「变更记录」。

| 层级 | 技术 | 说明 |
|---|---|---|
| 语言 | **Java 21 (LTS)** | 全栈后端语言 |
| Web 框架 | **Spring Boot 3.2+ + Spring WebFlux** | 响应式 REST，SSE 流式输出 |
| 安全/鉴权 | Spring Security 6 + OIDC/JWT | 企业 SSO、API Key |
| Agent 编排 | **LangGraph4j**（状态图）/ Spring AI Alibaba Agent Framework | 条件路由 / 循环 / 人工审批 |
| LLM 抽象 | **Spring AI 1.0 + LangChain4j** | 模型接入、RAG、工具调用 |
| 模型接入 | OpenAI 兼容接口 | 默认 DeepSeek / Qwen，支持本地 Ollama / vLLM，可自由配置 |
| 向量库 | **PostgreSQL 16 + pgvector**（主，与业务库同库）/ Milvus（备） | 向量索引与过滤检索 |
| 关键词检索 | Lucene BM25（本地）/ pg_search | 混合检索的稀疏通道 |
| 重排序 | bge-reranker（TEI 本地 / 远端 API） | 精排 Top-N |
| Embedding | bge-m3（TEI 本地 / 远端 API） | 中英文向量化 |
| 文档解析 | Apache Tika + Apache PDFBox + Apache POI + Tesseract/PaddleOCR | PDF/Word/Excel/PPT/图片/HTML |
| 关系库 | PostgreSQL 16（含 pgvector） | 元数据、权限、会话、审计、向量 |
| 缓存 | Redis 7（Spring Cache / Redisson） | 缓存、限流、会话 |
| 消息队列 | RabbitMQ 3.13（Spring AMQP）/ RocketMQ | 异步文档处理、事件 |
| 异步任务 | Spring Batch / Quartz | 批量入库、定时任务 |
| 对象存储 | MinIO（S3 兼容） | 原始文档与中间产物 |
| 流式输出 | WebFlux SseEmitter | 答案逐 token 返回 |
| 开放协议 | REST / WebSocket / **MCP**（Spring AI MCP） | 工具与数据源标准化接入 |
| 可观测 | Langfuse（LLM 观测）+ Micrometer + Prometheus + Grafana | 追踪、指标、评估 |
| 部署 | Docker Compose（开发）/ Kubernetes（生产） | Nginx + HTTPS |
| 认证 | Spring Security + OIDC / JWT + API Key | 企业 SSO、OpenAPI 鉴权 |

### 2.1 技术选型原则

1. **私有化优先**：核心模型与数据可完全离线部署（Qwen + Ollama / vLLM 兜底）。
2. **协议解耦**：LLM 通过 OpenAI 兼容层接入，向量库、Embedding、Reranker 均可插拔。
3. **编排优于提示**：复杂任务用 LangGraph4j 状态图显式建模，而非堆砌提示词。
4. **可观测可评估**：每次 LLM 调用必须有 trace，每个 RAG 结果必须有评估分数。
5. **最小可运行**：MVP 阶段允许只用 pgvector + 单一模型跑通闭环，再逐步替换为生产组件。

### 2.2 与 Java 技术背景的契合点（简历价值）

- 以 **Spring Boot 3 微服务 + Spring Security + RabbitMQ + Redis + PostgreSQL** 为主线，覆盖 Java 后端企业级开发主流能力。
- AI 侧通过 **Spring AI + LangChain4j + LangGraph4j + MCP** 体现「给传统 Java 项目接入 AI」的工程化能力，正是当前企业最需要的复合型技能。
- 向量检索与业务数据同库（pgvector），降低运维成本，体现架构取舍能力。

## 3. 系统模块划分（统一命名）

| 模块 | 英文标识 | 职责 |
|---|---|---|
| 知识库管理 | `kb` | 空间、文档、版本、标签、权限 |
| 文档处理管线 | `ingestion` | 上传→解析→切分→向量化→入库 |
| 检索引擎 | `retrieval` | 查询改写→混合检索→重排→上下文组装 |
| Agent 编排 | `agent` | 意图路由、工具调用、多智能体协同 |
| 工具与 MCP | `tools` | 内置工具 + MCP Server 接入 |
| 会话与记忆 | `memory` | 短期会话、长期记忆、上下文压缩 |
| 引用与溯源 | `citation` | 答案片段级引用、可验证跳转 |
| 管理与可观测 | `admin` | 评估、审计、指标、计费 |
| 开放平台 | `openapi` | API Key、配额、Webhook |

### 3.1 核心数据流

**知识入库流**
```
上传 → 解析 → 切分 → 向量化 → 混合索引 → 元数据入库 → 可检索
```

**智能问答流**
```
提问 → 会话管理 → 查询改写 → 权限过滤检索 → 混合召回 → 重排
     → 上下文组装(含引用) → Agent 编排/工具调用 → LLM 生成
     → 引用校验 → 流式返回 → 记录 trace/审计
```

**多智能体协同流**
```
Planner(拆解任务) → Worker(执行子任务) → Validator(校验) → 汇总
   ↳ 可路由至 检索Agent / 数据分析Agent / 业务系统Agent
```

## 5. 统一术语表

| 术语 | 含义 |
|---|---|
| RAG | 检索增强生成（Retrieval-Augmented Generation） |
| 混合检索 | 稀疏(BM25) + 稠密(向量) 双通道召回后融合 |
| Rerank | 对召回结果做精排 |
| 查询改写 | 将口语化问题改写为利于检索的多个子查询 |
| 上下文工程 | 动态组织送入模型的上下文（检索片段+记忆+指令） |
| MCP | Model Context Protocol，模型上下文协议，统一工具/数据源接入 |
| Function Calling | 模型按需调用函数/工具的能力 |
| LangGraph4j | Java 版 LangGraph，基于状态图的 Agent 编排框架 |
| 引用溯源 | 答案对应原文片段并可跳转验证 |
| 幻觉 | 模型生成无依据内容的现象 |
| 租户 | 多企业隔离的独立数据与配置单元 |

## 6. 文档编写规范

1. 每个文档必须包含：**元信息头**（版本、作者、状态、更新日期）、正文、变更记录。
2. 技术名词中英对照：首次出现写「中文（English）」。
3. 需求条目使用 **MoSCoW** 标注优先级：Must / Should / Could / Won't。
4. 设计条目标注 **MVP / V1 / V2** 阶段归属。
5. 所有接口、表名、字段名使用英文小写下划线风格，如 `conversation_id`。
6. 文档间引用使用相对路径，禁止绝对路径。
7. 每份文档结尾附「关联文档」一节，形成可追溯关系。
