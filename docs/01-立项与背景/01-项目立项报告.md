## 1. 项目背景与问题陈述

### 1.1 业务背景

企业经过多年信息化建设，沉淀了制度规范、SOP（Standard Operating Procedure，标准作业程序）、产品文档、技术资料、培训材料等大量非结构化知识资产。这些资产分布在 Wiki、网盘、即时通讯群聊、邮件与业务系统附件中，缺乏统一入口与统一检索手段。

随着大语言模型（Large Language Model，LLM）能力成熟，业界已验证「RAG（检索增强生成，Retrieval-Augmented Generation）」可将企业私有知识转化为可问答的能力。本项目「星枢 Nexus · 企业智能知识库与问答智能体平台（代号 NKAP）」即在此背景下提出：以**私有化 / 混合部署**为前提，将企业分散知识统一接入，通过 **RAG + Agent 编排（Agent Orchestration）**，为员工提供**可溯源、带权限、可扩展**的智能问答与业务协同能力。

### 1.2 问题陈述（Problem Statement）

经对目标企业客户进行初步调研，当前存在以下五类核心问题：

| 编号 | 问题 | 现状表现 | 量化影响（估算） |
|---|---|---|---|
| P1 | **知识分散** | 制度、SOP、产品文档散落在 Wiki / 网盘 / 群聊，检索靠人工 | 单次找资料平均耗时 8–15 分钟，日均检索行为占员工工作时长 8%–12% |
| P2 | **回答不可信** | 传统关键词检索只给链接，员工仍需自行阅读、判断 | 关键问题误答率不可量化，知识复用率低于 30% |
| P3 | **重复劳动** | HR、IT、客服、运维等支持类岗位大量重复解答相同问题 | 支持类咨询中约 60%–70% 为重复性问题 |
| P4 | **权限与合规** | 知识一旦接入 AI，无法保证「谁能问、能问什么、能看到哪段原文」可控可审计 | 多数企业出于数据安全顾虑推迟或放弃 AI 知识化项目 |
| P5 | **接入成本高** | 业务系统工具不统一，AI 难以调用真实业务数据 | 定制化集成成本高，跨系统工具复用率低于 15% |

### 1.3 问题根因分析

- **P1 / P2 的根因**：知识未被结构化索引，且缺少「检索 → 生成 → 引用」的闭环，模型无可靠依据。
- **P3 的根因**：知识供给侧与需求侧之间没有自助式通道，支持类岗位承担了人工知识分发职能。
- **P4 的根因**：多数平台以「返回整段文档」为粒度，缺少**片段级引用溯源（Citation）**与权限过滤（Permission Filtering）能力。
- **P5 的根因**：缺少统一工具接入协议，每个业务系统都要单独开发适配。

## 2. 项目目标与成功标准

### 2.1 北极星指标（North Star Metric）

**员工在 2 个点击内获得「带原文引用、可验证」的问题答案。**

> 北极星指标拆解：
> - **「2 个点击内」** = 入口点击 1 次 + 结果页查看引用 1 次，不要求用户跳转原文系统即可判断答案可信度。
> - **「带原文引用」** = 每个答案片段必须绑定可验证的出处（文档名 + 章节 + 原文片段 + 可跳转链接）。
> - **「可验证」** = 用户点击引用可直达原文对应位置，且该片段受当前用户权限约束。

### 2.2 目标分解与量化成功标准

| 编号 | 目标类别 | 成功标准 | 验证方式 |
|---|---|---|---|
| G1 | 效率目标 | 支持类岗位重复咨询量下降 **30%** | 上线前后各取 3 个月客服/HR/IT 咨询工单统计对比 |
| G2 | 覆盖目标 | 首期接入 **≥ 3 个业务域、≥ 1000 份文档、≥ 50 个 API 工具** | 平台 `kb` / `tools` 模块计数报表 |
| G3 | 质量目标 | RAG 回答**引用准确率 ≥ 90%** | `admin` 模块评估集抽样 + 用户负反馈（点赞/点踩）口径 |
| G4 | 质量目标 | **无依据回答率 ≤ 5%** | 幻觉（Hallucination）抽检，标注「答案无检索依据」占比 |
| G5 | 体验目标 | **2 次点击内**获得带引用答案 | 会话埋点统计「提问 → 点击引用」步数分布 |
| G6 | 合规目标 | 所有 LLM 调用可审计、权限过滤 100% 生效 | `admin` 审计日志抽查，越权检索用例回归 |
| G7 | 性能目标 | P95 首 token 延迟 ≤ 3s，完整答案 ≤ 15s（流式 SSE，与 NFR-001/002 口径一致） | Prometheus / Grafana 指标 |

### 2.3 分阶段里程碑

| 阶段 | 周期 | 关键交付 | 出口标准 |
|---|---|---|---|
| MVP | M1–M3 | PostgreSQL 16 + pgvector（Vector Database，向量库）+ 单一模型跑通「上传→检索→问答→引用」闭环 | G3 引用准确率 ≥ 80%，G6 权限过滤生效 |
| V1 | M4–M6 | PostgreSQL 16 + pgvector 混合检索、LangGraph4j（Java 版 LangGraph）状态图编排、MCP（Model Context Protocol，模型上下文协议）工具接入、评估体系 | G1/G2/G3/G4/G7 全部达标 |
| V2 | M7–M9 | 多租户、长期记忆、多智能体协同、OpenAPI 开放平台 | G5 及多租户隔离验收通过 |

## 3. 项目范围

### 3.1 In Scope（本期范围内）

| 编号 | 范围项 | 优先级（MoSCoW） | 阶段归属 | 对应模块 |
|---|---|---|---|---|
| S1 | 文档上传、解析、切分、向量化、入库全管线 | Must | MVP | `ingestion` |
| S2 | 混合检索（BM25 + 向量）与重排（Rerank） | Must | MVP | `retrieval` |
| S3 | 带片段级引用溯源的问答与流式输出（SSE） | Must | MVP | `citation` / `memory` |
| S4 | 基于权限过滤的检索与引用可见性控制 | Must | MVP | `retrieval` / `citation` |
| S5 | LangGraph4j 意图路由与工具调用编排 | Must | V1 | `agent` |
| S6 | 内置工具 + MCP Server 标准化接入 | Must | V1 | `tools` |
| S7 | 会话管理与短期记忆、上下文压缩 | Must | V1 | `memory` |
| S8 | LLM 可观测（Langfuse）与评估打分 | Must | V1 | `admin` |
| S9 | 多租户隔离与 OIDC / JWT 认证 | Must | V1 | `admin` |
| S10 | OpenAPI 开放平台（API Key、配额、Webhook） | Should | V2 | `openapi` |
| S11 | 长期记忆与多智能体协同（Planner/Worker/Validator） | Should | V2 | `agent` / `memory` |
| S12 | 计费与租户运营报表 | Could | V2 | `admin` |

### 3.2 Out of Scope（本期明确不做）

| 编号 | 排除项 | 排除理由 |
|---|---|---|
| O1 | 通用公有云联网搜索与外部互联网问答 | 私有化部署前提下数据不出域 |
| O2 | 模型训练与微调（Fine-tuning）服务 | 首期以 RAG 为主，不引入训练成本与合规风险 |
| O3 | 音频、视频内容的端到端问答 | 仅保留文档/图片等静态多模态文档理解 |
| O4 | 知识众包编辑与协作文档能力 | 沿用企业现有 Wiki，平台只做接入 |
| O5 | 移动端原生 App | 首期以 Web 端为主，API 可供第三方接入 |
| O6 | 复杂事务型流程引擎（如替代 OA/ERP） | 仅提供工具调用与编排，不承载业务交易 |

## 4. 干系人分析

| 角色 | 标识 | 核心诉求 | 影响力 | 沟通策略 |
|---|---|---|---|---|
| 平台管理员 | `admin` | 系统稳定、配额可控、审计完备、模型可替换 | 高 | 双周技术同步会 + 指标周报，重点沟通可观测与合规 |
| 知识库管理员 | `kb_admin` | 上传便捷、权限配置清晰、切分效果可调 | 高 | 需求共创工作坊，提供知识入库看板与权限演练环境 |
| 普通员工 | `employee` | 答案准确、引用可信、响应快、操作简单 | 中 | 试点期收集点赞/点踩反馈，月度体验报告 |
| 开发者 | `developer` | API 文档完善、鉴权简单、配额透明、Webhook 可靠 | 中 | 提供 OpenAPI 沙箱与联调环境，Release Note 驱动 |
| IT 运维 | —（非角色，属外部干系人） | 私有化部署、离线可用、监控告警、升级平滑 | 高 | 部署手册评审 + 灾备演练，纳入上线门禁 |
| 安全与合规部门 | —（非角色，属外部干系人） | 数据分类分级、越权防护、内容安全、留痕审计 | 高 | 合规评审前置，每次迭代提供安全测试报告 |
| 企业管理层 / 决策层 | —（非角色，属外部干系人） | 投入产出比、风险可控、可复制推广 | 高 | 立项/阶段门评审，聚焦量化收益与里程碑 |
| 业务域负责人（HR/IT/客服/运维） | —（非角色，属外部干系人） | 本域知识准确、咨询量下降、工具可调用 | 中 | 领域知识验收签字，联合定义本域评估集 |

> 说明：干系人中前四类为基线定义的平台用户角色，后四类为项目推进过程中必须协同的外部干系人。

## 6. 立项理由与预期收益

### 6.1 定量收益（年度估算）

| 收益项 | 测算逻辑 | 年化收益（估算） |
|---|---|---|
| 支持类咨询量下降 | 重复咨询降 30%，假设首年 500 名员工 × 人均年咨询 60 次 × 单次处理成本 15 元 × 30% | 约 135 万元 |
| 知识查找效率提升 | 日均检索 8%–12% 工时，单次找资料从 10 分钟降至 2 分钟 | 约 200–400 万元 |
| 新员工上手提速 | 培训周期缩短约 30% | 约 80–150 万元 |
| 文档维护成本下降 | 文档复用率提升，重复编写减少约 20% | 约 40–80 万元 |
| **合计（首年）** | | **约 455–765 万元** |

> 结论：按首年估算，项目收益与投入基本持平并具备正向回报，第二年随覆盖范围扩大将进入显著收益区间（预计 ROI ≥ 150%）。

### 6.2 定性收益

1. **知识资产化**：将分散文档转化为可检索、可问答、可运营的企业知识资产。
2. **决策可信化**：答案带原文引用，减少「凭经验作答」带来的误判风险。
3. **服务自助化**：支持类岗位从重复答疑转向高价值处理，组织效能提升。
4. **合规可控化**：权限级引用与全链路审计，为企业 AI 应用建立信任基线。
5. **生态可扩展**：MCP 工具生态与 OpenAPI 开放平台，形成可持续扩展的能力底座。
