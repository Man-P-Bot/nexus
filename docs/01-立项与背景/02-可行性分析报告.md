## 1. 技术可行性

### 1.1 关键技术成熟度评估

| 技术 | 中英对照 | 成熟度 | 证据/依据 | 本项目采用方式 |
|---|---|---|---|---|
| LangGraph4j | Java 版 LangGraph，基于状态图的 Agent 编排框架 | 成熟（生产可用） | v0.2+ 已支持条件路由、循环、人工审批（Human-in-the-loop），与 Spring AI / LangChain4j 生态一致 | `agent` 模块显式编排，替代堆砌提示词 |
| RAG | 检索增强生成（Retrieval-Augmented Generation） | 成熟 | 已成为企业知识问答主流范式，检索增强生成方案业界广泛落地 | `retrieval` + `citation` 闭环 |
| 向量库 | Vector Database（PostgreSQL 16 + pgvector 主，与业务库同库 / Milvus 备） | 成熟 | pgvector 与业务库同库降低运维成本；Milvus 支持大规模分布式向量检索 | 混合检索稠密通道 |
| MCP | 模型上下文协议（Model Context Protocol） | 快速成长期 | Anthropic 提出的开放协议，已获多厂商支持，工具接入标准化 | `tools` 模块统一工具/数据源接入 |
| 混合检索 | 稀疏（BM25，Best Matching 25）+ 稠密（向量）双通道 | 成熟 | Lucene BM25 / pg_search + pgvector 过滤检索，业界标准做法 | 召回阶段双通道融合 |
| 重排序 | Rerank（重排序，bge-reranker，TEI 本地 / 远端 API） | 成熟 | 精排 Top-N 可显著提升引用准确率 | `retrieval` 精排环节 |
| LLM 抽象 | LLM Abstraction（Spring AI 1.0 + LangChain4j） | 成熟 | 与 LangGraph4j 生态一致，统一 OpenAI 兼容接口 | 统一模型接入层 |
| 可观测 | Langfuse + Prometheus + Grafana | 成熟 | LLM 追踪、指标、评估一体化 | `admin` 模块观测与评估 |

**总体判断**：本项目所依赖的全部核心技术均已达到生产可用成熟度，不存在原理性障碍；风险集中在**工程集成与调优**层面，而非技术路线选择层面。

### 1.2 关键难点与验证方案

| 编号 | 关键难点 | 风险等级 | 验证方案（PoC） | 验收标准 | 对应模块 |
|---|---|---|---|---|---|
| T1 | **片段级引用溯源**：切分后引用定位到文档章节，跳转准确 | 高 | 取 100 份多格式文档，人工标注章节边界，测试引用跳转命中率 | 引用跳转命中率 ≥ 95% | `ingestion` / `citation` |
| T2 | **权限过滤正确性**：检索阶段即过滤，避免越权召回 | 高 | 构造跨空间/跨租户越权用例，回归测试引用可见性 | 越权召回用例 100% 拦截 | `retrieval` / `citation` |
| T3 | **中文长文档切分质量**：表格、多级标题、跨页内容被错误切断 | 高 | 对比 3 种切分策略（定长 / 语义 / 结构），评估检索命中率 | 检索命中率较基线提升 ≥ 20% | `ingestion` |
| T4 | **复杂 PDF / 扫描件解析**：表格、图片、扫描件识别率低 | 中 | 覆盖 PDF/Word/Excel/PPT/图片/HTML，含扫描件样本 | 解析字段准确率 ≥ 90% | `ingestion` |
| T5 | **Agent 编排稳定性**：工具调用失败、循环失控、超时 | 中 | 引入超时、重试、最大步数限制、人工审批节点 | 异常任务 100% 可控终止 | `agent` |
| T6 | **幻觉抑制**：模型生成无依据内容 | 高 | 引用校验环节 + 无依据回答抽检 | 无依据回答率 ≤ 5% | `citation` / `admin` |
| T7 | **私有化小模型质量**：本地模型效果低于云端主力模型 | 中 | 同一评估集对比 DeepSeek-V3 与 Qwen+Ollama | 小模型评估分 ≥ 主力模型 85% | `agent` / `admin` |
| T8 | **MCP 工具生态成熟度**：第三方 MCP Server 质量参差 | 中 | 先接 50 个内置工具，再以 MCP 接入业务系统 | 50 个工具联调通过 | `tools` |

### 1.3 最小可行闭环（MVP）技术验证结论

依据基线「最小可运行」原则，MVP 允许仅用 **PostgreSQL 16 + pgvector + 单一模型**跑通闭环：

```
上传 → 解析 → 切分 → 向量化 → pgvector 检索 → 上下文组装 → LLM 生成 → 引用校验 → 流式返回
```

- 该闭环可在 **8–10 周**内由 3–4 人团队完成，验证引用溯源、权限过滤、幻觉抑制三个高风险点。
- 生产组件（Milvus、混合检索、Rerank、LangGraph4j）在 V1 阶段按「协议解耦、可插拔」原则逐步替换，不影响 MVP 出口。

**技术可行性结论**：**可行**。技术路线成熟，风险可控，且具备清晰的降级与替换路径。

## 2. 经济可行性

### 2.1 成本收益模型

| 项目 | 首年（万元） | 次年（万元） | 说明 |
|---|---|---|---|
| 人力成本 | 600–750 | 150–250（运维为主） | 次年投入大幅下降 |
| 算力与基础设施 | 15–30 | 15–30 | 随文档量弹性 |
| 模型 API | 10–22 | 8–18 | 本地化占比提升可降低 |
| 安全合规 | 5–15 | 3–8 | 年度等保/渗透测试 |
| **成本合计** | **630–817** | **176–286** | — |
| **收益合计** | **455–765** | **700–1100** | 覆盖范围扩大 |
| **净收益** | **-175 ~ +135** | **+414 ~ +924** | 次年进入稳定收益期 |

### 2.2 ROI 估算模型

定义：

- 年化收益 `R` = 支持类咨询节约 + 知识查找效率节约 + 培训/文档节约
- 年化成本 `C` = 人力 + 算力 + API + 合规
- `ROI = (R - C) / C × 100%`

| 情景 | 首年 R | 首年 C | 首年 ROI | 次年 ROI |
|---|---|---|---|---|
| 保守 | 455 万 | 817 万 | -44% | 约 100% |
| 基准 | 600 万 | 700 万 | -14% | 约 170% |
| 乐观 | 765 万 | 630 万 | +21% | 约 330% |

> 敏感性分析：首年 ROI 对「重复咨询下降比例」与「覆盖员工数」最敏感。当重复咨询下降达 40% 或覆盖员工达 800 人时，首年即可转正。

### 2.3 成本控制要点

1. **私有化优先**：核心模型本地化部署，降低按量 API 成本与数据出域风险。
2. **分级模型策略**：简单问题用本地小模型，复杂问题用主力模型，控制单位查询成本。
3. **引用缓存**：高频问题答案片段缓存于 Redis，减少重复 LLM 调用。
4. **评估前置**：避免反复返工带来的隐性人力成本。

**经济可行性结论**：**可行**。首年基本持平，次年进入显著正回报区间，ROI 模型具备明确改善杠杆。

## 3. 运营可行性

### 3.1 组织接受度分析

| 干系人 | 潜在顾虑 | 应对措施 |
|---|---|---|
| 普通员工 | 担心答案不可信、被替代 | 强调「辅助而非替代」，引用可验证，先试点后推广 |
| 知识库管理员 | 担心知识维护负担加重 | 提供批量导入、自动切分预览、权限模板 |
| IT 运维 | 担心私有化部署与运维复杂度 | 提供 Docker Compose / Kubernetes 部署方案与监控告警 |
| 安全合规部门 | 担心数据越权与内容风险 | 权限过滤 100% 生效、全链路审计、内容安全策略 |
| 业务域负责人 | 担心知识质量不足影响本域 | 领域知识验收签字、联合定义评估集 |

### 3.2 流程改造

| 环节 | 现状 | 改造后 | 变更类型 |
|---|---|---|---|
| 知识沉淀 | 分散在 Wiki/网盘/群聊，无统一入口 | 统一接入 `kb` 空间，按业务域组织 | 流程新增 |
| 知识更新 | 人工通知、版本混乱 | 文档版本化，变更触发重新索引 | 流程优化 |
| 问题解答 | 人工答疑、重复劳动 | 自助问答为主，复杂问题转人工 | 流程重构 |
| 权限管理 | 文档级权限 | 文档级 + 片段级引用权限过滤 | 流程增强 |
| 效果反馈 | 无量化口径 | 点赞/点踩、评估分数、咨询量统计 | 流程新增 |

### 3.3 培训与推广

| 对象 | 培训内容 | 形式 | 时点 |
|---|---|---|---|
| 普通员工 | 如何提问、如何查看引用、如何反馈 | 线上培训 + 使用手册 | 试点上线前 |
| 知识库管理员 | 空间创建、上传、切分预览、权限配置 | 工作坊 + 操作手册 | 上线前 |
| 开发者 | OpenAPI、API Key、Webhook、配额 | 技术文档 + 沙箱联调 | V2 开放平台上线时 |
| 运维 | 部署、监控、备份、升级 | 部署演练 + 运维手册 | 上线前 |

**运营可行性结论**：**可行**。组织接受度可通过「先试点、后推广」降低阻力，流程改造与培训计划可落地。

## 4. 法律与合规可行性

### 4.1 适用法律法规

| 法规 | 核心要求 | 本项目对应措施 |
|---|---|---|
| 《数据安全法》 | 数据分类分级、安全保护义务 | 文档分类分级接入，权限隔离，安全审计 |
| 《个人信息保护法》 | 个人信息处理需合法、正当、必要 | 会话数据最小化采集，脱敏处理，明确告知与授权 |
| 《生成式人工智能服务管理暂行办法》 | 生成内容安全、训练数据合法、服务可追溯 | 私有化部署，内容安全策略，引用可溯源，模型来源合规 |
| 《网络安全法》及等保要求 | 网络安全等级保护 | 按等保要求部署，HTTPS、访问控制、日志留痕 |

### 4.2 内容安全与风险防控

| 风险 | 措施 |
|---|---|
| 生成内容违规 | 输入输出双重内容安全过滤，敏感词与风险分类模型 |
| 数据泄露 | 私有化/混合部署，传输加密（HTTPS），存储加密，最小权限 |
| 越权访问 | 检索阶段权限过滤 + 引用片段可见性校验 |
| 模型来源合规 | 采用合规商用模型与开源模型，明确授权与许可 |
| 用户误解风险 | 明确标注「AI 生成，仅供参考」，提供反馈入口 |

### 4.3 私有化部署对合规的意义

- **数据不出域**：核心模型与数据在企业内网完成，满足数据安全与保密要求。
- **可控可审计**：全链路 trace 与审计日志，满足监管留痕要求。
- **模型可替换**：可切换为合规备案的模型供应商，避免单一依赖。
- **降低授权风险**：避免将企业敏感数据提供给第三方公有云服务。

**法律与合规可行性结论**：**可行**。在私有化部署前提下，通过权限隔离、内容安全、审计留痕等措施，可满足主要法规要求；上线前需完成等保测评与安全测试。

## 6. 结论与建议

### 6.1 综合结论

| 维度 | 结论 | 关键依据 |
|---|---|---|
| 技术可行性 | **可行** | 全部核心技术生产可用，MVP 8–10 周可验证高风险点 |
| 经济可行性 | **可行** | 首年持平，次年 ROI 进入 100%–330% 区间 |
| 运营可行性 | **可行** | 试点推广降低阻力，流程与培训可落地 |
| 法律合规可行性 | **可行** | 私有化部署 + 权限过滤 + 内容安全满足主要法规 |

**总体结论：可行，建议进入需求阶段。**

### 6.2 MVP 建议

1. **聚焦单一业务域**：选择知识相对标准化、咨询量高的业务域（如 HR 制度）作为 MVP 试点。
2. **跑通三大高风险闭环**：引用溯源、权限过滤、幻觉抑制。
3. **技术降级起步**：MVP 使用 PostgreSQL 16 + pgvector + 单一模型，避免早期过度工程化。
4. **评估集先行**：同步建立 ≥ 200 条的领域评估集，作为质量基线。
5. **门控推进**：MVP 出口标准（引用准确率 ≥ 80%、权限过滤 100% 生效）达标后再进入 V1。
