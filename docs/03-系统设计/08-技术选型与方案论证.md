## 1. 选型原则与评估方法

### 1.1 选型原则

与基线「技术选型原则」保持一致，技术选型须遵循：

1. **私有化优先**：核心组件支持离线/内网部署，无强制依赖境外云服务。
2. **协议解耦**：LLM 走 OpenAI 兼容层，向量库/Embedding/Reranker 可插拔。
3. **编排优于提示**：复杂任务优先选择可显式建模的编排框架。
4. **可观测可评估**：每次 LLM 调用可追溯，每个 RAG 结果有评估分数。
5. **最小可运行**：MVP 允许降级组件跑通闭环，生产逐步替换。
6. **社区与许可证**：优先社区活跃、许可证商业友好、长期维护的项目。

### 1.2 评估维度

| 维度 | 权重（建议） | 评估方式 |
|---|---|---|
| 社区活跃度 | 高 | Star/Commit 频率、Issue 响应、生态插件、文档质量 |
| 企业成熟度 | 高 | 生产案例、稳定性、版本发布节奏、安全公告 |
| 私有化能力 | 高 | 是否支持离线部署、资源占用、镜像体积、License 限制 |
| 性能 | 中高 | 吞吐、延迟、内存、扩展性基准测试 |
| 许可协议 | 中高 | 是否允许商业闭源使用（Apache-2.0 / MIT 优先，GPL 慎用） |
| 学习成本 | 中 | 团队上手周期、文档与示例、招聘市场 |
| 与 Java 生态契合度 | 高 | 是否原生支持 Spring Boot 3 / Java 21、依赖冲突、工程化工具链 |

> 评估结论标注 **Must / Should / Could**，对应需求优先级；并标注 **MVP / V1 / V2** 阶段归属。

## 3. 关键方案论证

### 3.1 Agent 编排：LangGraph4j vs Spring AI Alibaba Agent Framework vs 纯 LangChain4j Chain vs 自研状态机

| 维度 | LangGraph4j（选定） | Spring AI Alibaba Agent Framework | 纯 LangChain4j Chain | 自研状态机 |
|---|---|---|---|---|
| 流程表达 | 状态图，条件边/循环原生 | 高层 Agent 编排，偏业务化 | 线性或简单分支 | 完全可控 |
| 人工审批 | 原生支持挂起/恢复 | 支持 | 需 hack | 需自建 |
| 可观测/回放 | 检查点可回放 | 一般 | 一般 | 需自建 |
| 多智能体 | 支持且灵活 | 原生，定制受限 | 弱 | 需自建 |
| Java 生态契合 | 高（Java 版 LangGraph） | 高（阿里生态） | 高 | 高 |
| 生态与社区 | LangGraph 生态，活跃 | 活跃，国内资料多 | 最成熟 | 无 |
| 学习成本 | 中高 | 中 | 低 | 高（开发成本） |
| 私有化 | 支持 | 支持 | 支持 | 支持 |
| 结论 | ✅ 选定 | ⚠️ V2 备选 | ❌ 复杂流程不可维护 | ❌ 重复建设成本高 |

**结论**：采用 **LangGraph4j**。复杂问答、工具调用、多智能体与人工审批均需可回放、可审计的状态机；LangGraph4j 在表达力、工程可控性与 Java 生态契合度上最优。MVP 阶段可先用单图问答链路，V1 再扩展多智能体；若团队偏好开箱即用的中文 Agent 框架，可在 V2 评估 Spring AI Alibaba Agent Framework。

### 3.2 RAG 检索：Lucene BM25 + pgvector 混合 vs 纯向量 vs 多路召回

| 维度 | 混合检索（选定） | 纯向量 | 多路召回 |
|---|---|---|---|
| 精确术语/编号 | 强 | 弱（易漏） | 强（可加规则召回） |
| 语义泛化 | 强 | 强 | 强 |
| 实现复杂度 | 中 | 低 | 高 |
| 延迟/算力 | 中 | 低 | 高 |
| 长尾召回 | 中 | 弱 | 强 |
| 可解释性 | 高（双通道） | 中 | 中 |
| 引用准确率支撑 | 强 | 弱 | 强 |

**Rerank 的必要性**：双通道融合后排序仍存在偏差，尤其是 BM25 与向量分数量纲不一致。引入 bge-reranker-v2-m3（TEI 本地/远端）做精排可显著提升 Top-N 质量，是「引用准确率 ≥ 90%、无依据回答率 ≤ 5%」目标的关键手段。代价是额外推理开销，采用「粗排 Top-50 → 精排 Top-8」策略控制成本。

**结论**：MVP 可先用纯向量 + Rerank 跑通；V1 上线 Lucene BM25 + pgvector 向量混合召回 + Rerank；V2 视效果引入多路召回（规则/图谱/表格专用通道）。

### 3.3 模型策略：DeepSeek/Qwen 主力 + Ollama/vLLM 本地兜底

| 场景 | 主力模型 | 备选 | 兜底 | 说明 |
|---|---|---|---|---|
| 通用知识问答 | DeepSeek-V3 | Qwen2.5 | Ollama 本地小模型 | 质量优先，外部模型可用时走主力 |
| 高精度/复杂推理 | Qwen2.5 大尺寸 | DeepSeek-V3 | vLLM 本地模型 | 按任务路由 |
| 数据不出内网 | 本地 Ollama / vLLM 大模型 | — | 本地模型 | 合规优先 |
| 模型服务故障 | 自动降级至备选 | 本地模型 | 仅返回检索结果摘要 | 可用性优先 |

**理由**：
- 主力模型兼顾中文质量与成本，通过 OpenAI 兼容层接入，模型切换对业务透明。
- Ollama / vLLM 兜底保证私有化与故障降级两条底线；vLLM 适合高吞吐生产推理，Ollama 适合开发与轻量私有化。
- 路由策略按租户配置，满足不同客户合规等级差异。

**代价**：本地小模型质量与速度下降，需在体验与合规间权衡，并对降级结果做明确标识。

### 3.4 文档解析：Apache Tika + PDFBox/POI + OCR vs 自研解析 vs 商业解析服务

| 维度 | Apache Tika + PDFBox + POI + Tesseract/PaddleOCR（选定） | 自研解析 | 商业解析服务 |
|---|---|---|---|
| 格式覆盖 | PDF/Word/Excel/PPT/图片/HTML | 按需求覆盖 | 强（含复杂版面） |
| 表格/版面还原 | 中上 | 可控但成本高 | 上 |
| 私有化 | 支持 | 支持 | 依赖云端，私有化弱 |
| 许可协议 | Apache-2.0，商业友好 | 完全自主 | 商业授权 |
| 维护成本 | 中 | 高 | 低但受外部依赖 |
| 离线可用 | 是 | 是 | 否 |

**结论**：采用 **Apache Tika + PDFBox + POI + Tesseract/PaddleOCR** 组合。Tika 统一入口与格式探测，PDFBox/POI 负责原生格式深挖，Tesseract/PaddleOCR 补充扫描件识别；全部 Apache-2.0，可私有化。V2 可评估版面更强的开源方案（如 MinerU / marker）替换部分能力，或对非私有化场景引入商业解析服务。

### 3.5 向量库：pgvector vs Milvus vs Qdrant vs Elasticsearch

| 维度 | pgvector（选定） | Milvus | Qdrant | Elasticsearch |
|---|---|---|---|---|
| 过滤检索 | 强（与 SQL 联合） | 强 | 强 | 强 |
| 大规模性能 | 中（千万级需分区优化） | 优 | 优 | 中上 |
| 部署复杂度 | 极低（复用 PG） | 高（组件多） | 低 | 中 |
| 运维成本 | 低 | 高 | 中 | 中高 |
| 多租户 | 强（行级 + RLS） | 强 | 强 | 强 |
| 许可协议 | PostgreSQL License（宽松） | Apache-2.0 | Apache-2.0 | 部分组件 SSPL/Elastic License |
| 生态 | 活跃（随 PG） | 活跃 | 活跃 | 活跃 |
| 适用场景 | 生产主力（规模适中） | 超大规模备选 | 独立向量服务 | 已有 ES 技术栈 |

**结论**：生产主选 **pgvector**，因向量与业务元数据同库、权限过滤一次完成、运维仅需一套 PostgreSQL，契合「最小可运行」与私有化原则；向量规模或并发显著增长时，通过 Milvus 备库以统一 Provider 接口无缝切换。Qdrant 作为轻量独立向量服务备选；Elasticsearch 仅在客户已有栈或需统一全文检索时评估。

### 3.6 可观测：Langfuse vs 自研埋点

| 维度 | Langfuse（选定） | 自研埋点 |
|---|---|---|
| 私有化 | 支持 | 完全自主 |
| Trace | 完整，支持 LLM 调用链 | 需自建 |
| 评估 | 内置在线/离线评估 | 需自建 |
| 成本 | 开源自部署 | 研发成本高 |
| 与 Spring AI/LangChain4j 集成 | 提供 Java SDK，适配成本低 | 需适配 |
| 维护成本 | 中 | 高 |
| 指标/日志 | 与 Micrometer/Prometheus 互补 | 需自建 |

**结论**：采用 **Langfuse + Micrometer + Prometheus + Grafana** 组合。Langfuse 承担 LLM 侧 Trace 与评估，Micrometer/Prometheus 承担基础设施与业务指标，日志走结构化采集（JSON + trace_id）。避免自研埋点导致的重复建设；若后续评估需求复杂化，可在 V2 引入 Ragas 等专用评估框架。

### 3.7 MCP：Spring AI MCP 工具接入标准化

**必要性**：
- 企业工具异构（REST/SOAP/数据库/CLI），若逐一定制 Function Calling，接入与治理成本随工具数线性增长。
- MCP 提供统一工具发现、Schema 描述与调用协议，使工具接入标准化、可治理、可审计。
- 内置工具与外部工具走同一协议，降低心智负担与替换成本。

**落地方式**：
1. `tools` 模块内置 MCP Client（`Spring AI MCP`），统一连接 MCP Server 注册表。
2. 每类业务系统封装为独立 MCP Server，内置鉴权与租户隔离。
3. MCP 网关负责工具 Schema 校验、超时隔离、结果裁剪与敏感字段脱敏。
4. Agent 编排引擎通过 Function Calling 语义调用 MCP 工具，工具选择由模型决策，执行由网关约束。
5. 所有调用写入 Trace 与审计，便于计量与排障。

**风险控制**：MCP 规范仍在演进，锁定版本并抽象适配层，避免与具体实现强耦合；关键工具保留本地 Function Calling 降级路径。

## 5. 技术风险与替代预案

| 风险 | 影响 | 概率 | 应对与预案 |
|---|---|---|---|
| 开源许可证冲突（个别解析/向量组件） | 商用合规 | 中 | 选型阶段做 License 清单；不满足时替换为纯 Apache/MIT 组件 |
| LangGraph4j 版本迭代快、API 变动 | 维护成本 | 中 | 锁定版本，抽象编排适配层，避免业务直绑 API |
| Spring AI / LangChain4j 能力边界重叠 | 集成成本 | 中 | 明确职责：Spring AI 管模型接入，LangChain4j 补 RAG/工具，编排统一走 LangGraph4j |
| pgvector 超大规模性能瓶颈 | 检索性能下降 | 中 | 提前分区与 HNSW 参数调优；超大规模切换 Milvus 备库 |
| 本地小模型质量不足 | 体验下降 | 中高 | 按租户分级：合规场景接受降级；质量场景强制外部模型 |
| 文档解析复杂版面效果差 | 引用准确率下降 | 中 | 引入版面模型（MinerU/marker）或商业解析服务（非私有化场景），补充人工校验 |
| MCP 规范不成熟 | 工具接入返工 | 中 | 锁定版本 + 适配层 + 本地 Function Calling 降级路径 |
| 混合检索融合权重不当 | 召回质量下降 | 中 | 建立离线评估基线，定期 A/B 调整权重 |
| Rerank 推理算力开销大 | 延迟上升 | 中 | 粗排 Top-50 → 精排 Top-8；模型量化/批处理；按需开关 |
| 多租户权限过滤性能开销 | 延迟上升 | 中 | 权限条件下推到 pgvector 过滤，避免应用层二次过滤 |
| RabbitMQ 队列积压 | 入库延迟 | 中 | 独立队列与 Worker 扩缩容；优先级与死信治理 |
| 依赖组件安全漏洞 | 安全风险 | 中 | 依赖扫描纳入 CI，定期升级；关键组件灰度发布 |
| LLM 成本失控 | 预算风险 | 中 | 租户配额、模型路由、缓存命中、用量计量与告警 |

**总体预案原则**：每个核心能力（模型、向量库、解析、编排、消息队列）均保留至少一个可替换实现，通过接口抽象隔离，确保单一组件失效或合规受限时可快速切换，不破坏整体架构。
